# KJÁR — сервер и выкладка

## 0. Что развёрнуто сейчас

**Сервер:** Timeweb Cloud, Амстердам, 2 × 3.3 ГГц, 2 ГБ RAM, 40 ГБ NVMe, Ubuntu 26.04.
IP `72.56.67.219`. Swap 2 ГБ, ufw открывает 22, 80, 443.

**Почему не Россия.** На российской площадке с сервера не открывался `registry.npmjs.org`
(DNS резолвится, соединение висит), поэтому собрать образы на месте было невозможно.
Плюс входящий SSH оттуда работал нестабильно. В Амстердаме и npm, и ghcr, и SSH доступны.

**Как выкатывается.** `.github/workflows/deploy.yml`, две задачи:

1. **Сборка.** Раннер GitHub собирает два образа по `docker/Dockerfile.prod`
   и публикует их в `ghcr.io/dmitrybotyan/kjar-web` и `.../kjar-api`.
2. **Выкладка.** Раннер заходит на сервер по ключу, копирует конфиги, пишет
   `.env.production` из секрета, логинится в ghcr временным токеном задачи,
   тянет образы, применяет миграции, поднимает стек и ждёт ответа 200.

На сервере ничего не собирается: 2 ГБ памяти для `next build` мало, ему нужно до 2 ГБ
только под сборку. Лог каждой выкладки возвращается в репозиторий,
`.deploy-logs/last-deploy.log`.

**Секреты репозитория:** `SSH_HOST`, `SSH_USER`, `SSH_PORT`, `SSH_PRIVATE_KEY`,
`ENV_PRODUCTION`.

**Домен и сертификат.** `kjar.ru` и `www.kjar.ru` смотрят на сервер, сертификат
Let's Encrypt выпущен до 8 ноября 2026. HTTP отвечает редиректом на HTTPS, `www`
уходит на основной домен. Продление:

```
cd /opt/kjar && docker compose --env-file .env.production -f docker/docker-compose.prod.yml \
  --profile tools run --rm certbot renew && docker compose --env-file .env.production \
  -f docker/docker-compose.prod.yml restart nginx
```

**Первый администратор.** Роль `admin` через регистрацию не выдаётся, поэтому:

```
cd /opt/kjar && docker compose --env-file .env.production -f docker/docker-compose.prod.yml \
  exec -T -e ADMIN_PASSWORD='пароль' api node --import tsx src/scripts/createAdmin.ts логин "$ADMIN_PASSWORD"
```

Тем же скриптом меняется пароль существующего пользователя.

## 1. Что придётся держать на сервере

| Компонент | Что это | Память в простое (замер на dev) | Заметки |
|---|---|---|---|
| `web` | Next.js 14, Node 22 | ~590 МБ (dev) / ~250–350 МБ (prod) | в проде легче: нет watch и dev-оверлея |
| `api` | Express + Drizzle, Node 22 | ~140 МБ | |

## 2. Конфигурации

### Абсолютный минимум

**1 vCPU, 2 ГБ RAM, 25 ГБ NVMe, swap 2 ГБ, Ubuntu 24.04.**

Ниже 2 ГБ проект не поедет: Postgres, Node под API и Node под Next в сумме уже
занимают около гигабайта, остальное съест страничный кэш.

Условия, без которых этот минимум не работает:

1. **Образ собирать не на сервере.** `next build` берёт до 2 ГБ и на такой машине
   уйдёт в OOM. Собирать локально или в CI, на сервер класть готовый образ.
2. **MinIO не поднимать.** Картинки в объектное хранилище провайдера, это минус
   контейнер (около 100 МБ памяти) и минус рост диска.
3. **Adminer выключить.** В проде он не нужен.
4. **Swap обязателен**, иначе любой всплеск убьёт Postgres.

Замеры на рабочем стенде (dev, всё в одном docker compose):

| Контейнер | Память |
|---|---|
| web (Next в dev) | 565 МБ, в проде 250–350 МБ |
| api (Express) | 113 МБ |
| db (Postgres 16) | 23 МБ пустая, 150–400 МБ рабочая |
| minio | 107 МБ (на минимуме не ставим) |
| adminer | 11 МБ (на минимуме не ставим) |

Что получится: сайт открывается, читается, комментарии и ивенты работают. Чего не
будет: запаса на всплеск посещаемости во время массового ивента и возможности
собирать прямо на сервере.

### Минимум без компромиссов по сборке

**2 vCPU, 4 ГБ RAM, 40 ГБ NVMe.** Сборка проходит на самом сервере, MinIO можно
держать локально, база живёт свободно.

### Ещё дешевле: вынести базу

**1 vCPU, 1 ГБ RAM + managed PostgreSQL** у провайдера. На сервере остаются web,
api и nginx, это около 500 МБ. Дешевле по железу, дороже по услуге БД, зато бэкапы
и обновления Postgres не ваша забота.

### Рекомендуемый

- **2–4 vCPU, 4 ГБ RAM, 60 ГБ NVMe**
- сборка проходит прямо на сервере, БД и MinIO живут спокойно
- запас на рост базы, картинки ивентов и логи
- сотни визитов в день, десятки одновременных читателей — без вопросов

### С запасом (если планируются массовые ивенты)
- **4 vCPU, 8 ГБ RAM, 80–120 ГБ NVMe**
- комфортно, когда на ивент одновременно заходит толпа игроков и грузит картинки в комментарии

**Процессор:** обычные vCPU без гарантированной доли (shared) годятся. Node на пиковой
нагрузке любит частоту, поэтому если есть выбор «4 медленных ядра» против
«2 быстрых» — берите быстрые.

## 3. Диск и трафик

- Код + образы Docker: ~3–5 ГБ (один образ web ≈ 950 МБ, плюс слои и кэш сборки).
- База: старт < 100 МБ, реалистичный рост — единицы гигабайт за год.
- Картинки постов, ивентов и комментариев в MinIO: считайте по 1–3 МБ на изображение.
  1000 картинок ≈ 2–3 ГБ.
- Логи и бэкапы: заложите 10 ГБ.
- **Итого 60 ГБ — комфортный старт**, 30 ГБ придётся чистить руками.
- Трафик: у обоих провайдеров он безлимитный/щедрый на облачных тарифах, отдельно
  докупать не нужно. Ширина канала 100 Мбит/с и выше — достаточно.

## 5.1. Подготовка сервера: swap

Timeweb отдаёт VPS без swap. Сначала проверьте, вдруг он уже есть:

```bash
swapon --show
free -h
```

Пусто — создаём файл подкачки на 2 ГБ (для 4 ГБ RAM этого хватает):

```bash
sudo fallocate -l 2G /swapfile          # если fallocate не сработал:
                                        # sudo dd if=/dev/zero of=/swapfile bs=1M count=2048
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

Последняя строка нужна, чтобы swap подключался после перезагрузки.

Подкручиваем поведение: ядро должно уходить в swap только при реальной нехватке,
иначе Postgres начнёт тормозить на ровном месте.

```bash
sudo tee /etc/sysctl.d/99-swap.conf > /dev/null <<'EOF'
vm.swappiness=10
vm.vfs_cache_pressure=50
EOF
sudo sysctl --system
```

Проверка:

```bash
swapon --show     # должен появиться /swapfile, 2G
free -h           # в строке Swap те же 2G
```

Что важно понимать: swap не добавляет памяти, он спасает от падения при пике. Если
`free -h` показывает, что swap занят постоянно, значит машине мало RAM и пора
увеличивать тариф. На 25 ГБ диска файл на 2 ГБ забирает 2 ГБ места, это заложено.

## 6. Сеть и безопасность

- Наружу открыты только **80 и 443**.
- **22** — по ключу, пароль отключить (`PasswordAuthentication no`), лучше сменить порт.
- Порты `3000`, `3001`, `5433`, `9000/9001`, `8081` (adminer) **не публиковать наружу** —
  в production-compose оставить их только во внутренней сети.
- Firewall: ufw или облачный firewall провайдера.
- fail2ban на ssh.
- Секреты (`JWT_SECRET`, пароль БД, ключи S3) — сгенерировать заново, не брать dev-значения из `.env`.

## 7. Timeweb Cloud или REG.RU

Оба подходят, разница небольшая:

**Timeweb Cloud** — облачные серверы в Москве и Санкт-Петербурге, S3-совместимое
хранилище и managed PostgreSQL в одном кабинете, снапшоты по расписанию, почасовая
оплата (удобно тестировать). Обычно берут его.

**REG.RU** — VPS и облако с ЦОД в Москве и СПб, домен и сервер в одном месте.
Объектное хранилище и managed БД тоже есть.

Оба держат данные в РФ — для 152-ФЗ это то, что нужно (у нас в базе есть e-mail
пользователей и комментарии).

**Регион:** для игроков из европейской части России Москва и СПб равнозначны, разница
в задержке — единицы миллисекунд. Берите Москву, если провайдер даёт там больший
выбор конфигураций.

## 8. Готовность к переносу

Продакшн-обвязка написана и проверена локальной сборкой:

| Файл | Что делает |
|---|---|
| `docker/Dockerfile.prod` | multi-stage: зависимости, сборка Next в standalone, отдельные рантаймы web и api |
| `docker/docker-compose.prod.yml` | db, api, web, nginx; наружу торчит только nginx, база и api внутри сети; профиль `tools` для миграций и certbot |
| `docker/nginx/kjar.conf` | прокси на web, ACME-челлендж, заготовка блока 443 |
| `.env.production.example` | шаблон боевых переменных, включая строгий лимит запросов |
| `scripts/server-bootstrap.sh` | на сервере: swap, docker, ufw, каталог `/opt/kjar` |
| `scripts/deploy.sh` | с локальной машины: rsync, сборка, миграции, запуск |
| `.dockerignore` | без него `COPY . .` затирал модули симлинками pnpm |

Проверено на локальной машине: стек поднимается, миграции применяются, все девять
маршрутов отдают 200, стили и статика на месте.

Расход памяти в продакшн-режиме заметно ниже, чем в dev:

| Контейнер | dev | prod |
|---|---|---|
| web | 565 МБ | **51 МБ** |
| api | 113 МБ | 111 МБ |
| db | 23 МБ | 10 МБ |
| nginx | — | 4 МБ |

Итого около 175 МБ против 700 МБ в dev. На сервере с 4 ГБ запас большой.

Три грабли, на которые напоролся при сборке (уже обойдены, но знать полезно):

1. **pnpm + standalone.** Next копирует `node_modules` как есть, а pnpm кладёт туда
   симлинки на `.pnpm`, которые в образе указывают в никуда. Лечится `node-linker=hoisted`
   на этапе установки.
2. **Отсутствие `.dockerignore`.** Локальные `node_modules` попадали в контекст и
   затирали установленные в образе.
3. **Монорепо и трассировка файлов.** Без `experimental.outputFileTracingRoot` standalone
   собирается без `node_modules`, сервер падает с `Cannot find module 'next'`.

### Что осталось сделать при переносе

1. Домен направить на сервер, после этого выпустить сертификат (`--profile tools run --rm certbot`)
   и раскомментировать блок 443 в `docker/nginx/kjar.conf`.
2. Заполнить `.env.production`: новые пароль базы и `JWT_SECRET` (`openssl rand -hex 32`),
   боевые `CORS_ORIGIN` и `NEXT_PUBLIC_SITE_URL`, ключи объектного хранилища.
3. Сид на боевую базу **не запускать**: он очищает таблицы. Контент заводится через `/admin`.
   Первого администратора создать вручную через `POST /api/v1/auth/register` и поднять ему
   роль в базе.
4. Настроить автобэкап: `pg_dump` по cron с выгрузкой в объектное хранилище.
5. После установки ключа закрыть вход по паролю: `PasswordAuthentication no`.
